# 포트폴리오 기술 정리: Budget Meal Finder

## 사용 기술스택
- Backend: Node.js, Express.js, JWT, Bcrypt, Multer
- Database: MongoDB, Mongoose (Geospatial Indexing)
- Frontend: Vanilla JavaScript (ES Modules), Google Maps API, CSS3
- Infrastructure: Docker, Docker Compose
- Documentation: Swagger (OpenAPI 3.0)

---

## 프로젝트에 대한 개요
"위치 기반 가성비 식당 검색 및 커뮤니티 플랫폼"
사용자의 현재 위치를 기반으로 저렴하고 질 좋은 식당 정보를 실시간으로 제공하며, 사용자들이 직접 메뉴를 등록하고 추천/비추천을 통해 신뢰도 높은 데이터를 구축하는 풀스택 웹 서비스입니다.

---

## 기능 + 문제 + 해결 + 결과

### 1. 실시간 위치 기반 주변 메뉴 검색 (핵심 기능)
- 기능: 사용자의 현재 좌표 또는 지도 중심 좌표를 기준으로 반경 내의 메뉴 정보를 거리순으로 제공.
- 문제: 데이터 규모가 커질 경우 모든 메뉴의 좌표를 계산하여 필터링하는 방식은 검색 성능이 급격히 저하됨.
- 해결: MongoDB의 2dsphere Geospatial Index와 $near 연산자를 도입하여 데이터베이스 레벨에서 거리 기반 쿼리 최적화.
- 결과: 수백만 건의 데이터셋에서도 O(log N) 수준의 빠른 검색 속도를 확보하여 실시간 지도 탐색 환경 구축.

### 2. 다중 조건 복합 검색 최적화
- 기능: 키워드, 가격대, 카테고리, 정렬 기준(추천수/최신순)을 결합한 상세 검색.
- 문제: 여러 필터 조건이 중첩될 때 각기 다른 인덱스를 타거나 다수의 쿼리가 발생하여 응답 시간이 길어지는 문제 발생.
- 해결: MongoDB Aggregation Pipeline을 설계하여 데이터 가공 및 필터링 로직을 DB 내부에서 단일 파이프라인으로 처리.
- 결과: 서버-DB 간 네트워크 오버헤드를 최소화하고, 복잡한 검색 요청에 대해 일관된 빠른 응답 성능 달성.

### 3. 지도 마커 렌더링 최적화 (UX 개선)
- 기능: 검색된 수많은 식당 위치를 구글 지도 위에 마커로 표시.
- 문제: 특정 지역에 식당이 밀집되어 있을 경우, 수천 개의 마커를 브라우저가 한 번에 렌더링하면서 화면 끊김 및 과부하 발생.
- 해결: Marker Clustering(마커 클러스터링) 기법을 적용하여 밀집된 데이터를 그룹화하고, 확대 수준(Zoom level)에 따라 동적으로 개별 마커 노출.
- 결과: 대규모 데이터 표시 중에도 쾌적한 지도 조작(드래그, 줌) 경험 제공 및 브라우저 메모리 점유율 감소.

### 4. 확장성 있는 아키텍처 설계
- 기능: 사용자 인증, 메뉴 관리, 관리자 도구 등 다양한 비즈니스 로직 구현.
- 문제: 초기 코드 작성 시 로직이 컨트롤러에 집중되어 코드 중복이 심화되고 유지보수 및 테스트가 어려워짐.
- 해결: Layered Architecture (Controller-Service-Repository) 패턴을 도입하여 관심사를 분리하고 비즈니스 로직을 서비스 계층으로 캡슐화.
- 결과: 코드 가독성 향상, 신규 기능 추가 시 기존 코드 수정 최소화(유지보수성 증대), 단위 테스트 작성이 용이한 구조 확보.

## 예상 면접 질문 및 답변 (Q&A)

질문 1: 애플리케이션 코드에서 거리 계산(Haversine 공식 등)을 하지 않고 MongoDB Geospatial Index를 사용한 이유는 무엇인가요?
답변: 애플리케이션 레벨에서 거리를 계산하려면 DB에서 전체 데이터를 메모리로 로드한 뒤 루프를 돌며 계산해야 하므로 데이터가 늘어날수록 O(N)의 시간 복잡도가 발생합니다. 반면 MongoDB의 2dsphere 인덱스는 위치 데이터를 공간 계층 구조(S2 Geometry 등)로 관리하여 인덱스 스캔만으로 주변 데이터를 필터링하므로, 대규모 데이터셋에서도 매우 빠르고 효율적인 검색이 가능하기 때문입니다.

질문 2: Aggregation Pipeline을 사용할 때 성능상 주의해야 할 점은 무엇인가요?
답변: 파이프라인의 순서가 매우 중요합니다. 특히 $match나 $geoNear 같은 필터링 단계는 반드시 파이프라인의 가장 앞부분에 배치해야 합니다. 인덱스를 탈 수 있는 단계를 초반에 배치하여 처리해야 할 도큐먼트의 수를 최대한 줄여야만 전체 파이프라인의 메모리 사용량과 처리 속도를 최적화할 수 있습니다.

질문 3: 마커 클러스터링을 적용하지 않았을 때 브라우저에서 어떤 성능 병목이 발생하나요?
답변: 수천 개의 마커를 한 번에 지도에 그리면, 브라우저는 각각의 마커를 독립적인 DOM 요소나 캔버스 객체로 관리해야 합니다. 이는 메인 스레드의 점유율을 높여 지도를 드래그하거나 확대/축소할 때 프레임 드랍(화면 끊김)을 유발하며, 브라우저의 메모리 소비를 급격히 증가시켜 탭이 멈추거나 꺼지는 현상을 초래할 수 있습니다.

질문 4: Controller와 Service 계층을 분리함으로써 얻은 실질적인 이점은 무엇이었나요?
답변: 가장 큰 이점은 비즈니스 로직의 재사용성과 테스트 용이성입니다. 예를 들어, 동일한 메뉴 추천 로직을 웹 API뿐만 아니라 관리자 대시보드나 배치 작업에서도 호출해야 할 때, Controller에 로직이 있다면 중복 코드가 발생하지만 Service에 있으면 해당 함수만 호출하면 됩니다. 또한 DB나 프레임워크에 의존하지 않는 순수 비즈니스 로직에 대해 단위 테스트를 독립적으로 수행할 수 있게 되었습니다.

질문 5: JWT 토큰 방식의 인증을 선택하셨는데, 토큰이 탈취되었을 때의 보안 취약점은 어떻게 보완할 수 있을까요?
답변: JWT는 한 번 발급되면 만료 전까지 유효하므로 탈취 시 위험할 수 있습니다. 이를 보완하기 위해 Access Token의 만료 시간을 짧게(예: 15분) 설정하고, 대신 갱신을 위한 Refresh Token을 안전한 곳(HttpOnly Cookie)에 저장하여 관리하는 방식을 도입할 수 있습니다. 또한, 로그아웃 시나리오에서는 Redis 같은 인메모리 DB를 활용해 해당 토큰을 블랙리스트에 등록하여 즉시 무효화하는 전략을 고려할 수 있습니다.

## 기타 구현 기능
- JWT 인증 시스템: Stateless 인증을 통한 서버 부하 감소 및 보안성 확보.
- 이미지 업로드 (Multer): 메뉴 사진 등록 및 정적 자산 관리 기능.
- 추천/비추천 시스템: 사용자 간 상호작용 및 데이터 신뢰도 강화를 위한 투표 로직.
- 관리자 관리 도구: 전체 사용자 및 게시물에 대한 모니터링 및 제어 기능.
- Swagger API 문서화: 협업 효율을 위한 표준화된 인터페이스 명세서 자동 생성.
- Docker 컨테이너화: 개발-검증-운영 환경의 일관성을 위한 환경 격리 및 배포 준비.
